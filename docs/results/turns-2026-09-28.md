# LLM turns from what the proxy sees

The proxy sees an agent's tool calls, not its LLM turns, so stretto infers the turns. Until now a call joined the current turn only while an earlier call of it awaited its response. Claude Code runs a turn's calls as the model streams them, so a call can reach the proxy after an earlier call of the same turn has returned. The proxy then counted it as a new turn. [The live promotion on AgentDojo's Slack suite](live-benchmarks-2026-09-27.md#promotion-on-the-agents-own-sessions-live) showed the cost: `stretto promote` counted those calls as the agent using the flow's lookups, and the lookups it promoted spared nothing ([issue #40](https://github.com/alexnodeland/stretto/issues/40)).

This round measures the rule against the host's own record of the turns, changes it, and makes `promote` score a lookup as the proxy would make it.

## Findings

- **Overlap alone split most turns of several calls.** In 285 of [the live benchmark sessions](live-benchmarks-2026-09-27.md), Claude Code recorded which calls each LLM turn made: 1,455 calls in 1,133 turns, 210 of them with several calls. Overlap alone split 122 of those 210, and found 1,320 turns in all. It never merged two turns.
- **The rest of a turn comes quickly, and a new turn does not.** Take a call sent after the turn's last response, with no call awaiting one:
  - When it was the same LLM turn, it came a median of 218 ms after that response, and 90% came within 572 ms.
  - A new LLM turn never came sooner than 850 ms, with a median of 4.0 s: the model reads the results first.
- **The new rule is 500 ms, unless a call needs what its turn returned.** A call sent within 500 ms of its turn's last response, with nothing said in between, now joins that turn. The exception is a call that passes a value first seen in what the turn returned, since the model could not have written it before reading the result. That rule found 1,157 turns for 1,133. It split 20 of the 210 turns of several calls, at 24 pairs of calls, and merged none.
  - Of the 24 splits, 21 are calls more than 500 ms after the response; the longest came 3.3 s after it.
  - The other 3 came from the exception. Each passed values the model had from the request, which the proxy does not see: a car's four door names in BFCL, and a file's name.
  - On these sessions, 500 ms alone never merged two turns, so the exception prevented nothing. It is for a host faster than Claude Code, or a script, that calls again within 500 ms with something the result gave it.
- **`promote` now scores a lookup as the proxy would make it.** The proxy decides as each result comes back. The calls of that turn still on their way are the agent's own, and it leaves them to the agent. `promote` now does the same. It follows a chain of lookups as the proxy does, and counts a lookup as used only when the agent makes the call in a later turn.
- **In Slack, promotion would now keep no site, and so no duplicate lookups.** On the agents' 12 training sessions, the sites promotion had kept now score none of their lookups used (the table below). So the promoted flow would make no lookups. Live, its 8 lookups had all been calls the agents made again themselves.
- **In τ²-bench, 23 of 24 promotions keep the same sites.** τ²-bench records each turn's calls, so the rule does not change those episodes. Only the scoring does. The one change held back `get_product_details` in one retail half at the loosest bar. On the replay, the flow saved the same 277 turns with 21 fewer lookups and 2 fewer detours.

## The rule, against Claude Code's record

The sessions are the live round's AgentDojo and BFCL episodes: Claude Code, with GLM-5.3 and Claude Haiku 4.5, without and with a flow, and the Slack training sessions. In each, Claude Code's event stream (`events.jsonl`) groups each LLM turn's tool calls under one message, and the proxy's log holds the same calls in the same order. The rule counts the agent's calls only, without the flow's own lookups, as the console counts turns. `scripts/turn_inference.py` mirrors `stretto_trace::mcp::episode` and agrees with it, call for call, on all 285 sessions.

A turn is split when a rule puts its calls in more than one turn. A pair of consecutive calls from one turn that a rule puts in two is a pair split, and a pair from two turns that it puts in one is a pair merged.

| Rule: a call with nothing awaiting a response joins the turn when it comes | Turns (1,133 in fact) | Turns split (of 210) | Pairs split | Pairs merged |
|---|---|---|---|---|
| never (overlap alone, before) | 1,320 | 122 | 187 | 0 |
| within 100 ms | 1,273 | 86 | 140 | 0 |
| within 250 ms | 1,212 | 53 | 79 | 0 |
| within 500 ms | 1,154 | 17 | 21 | 0 |
| **within 500 ms, unless it needs what the turn returned (now)** | **1,157** | **20** | **24** | **0** |
| within 1,000 ms | 1,123 | 6 | 6 | 16 |
| within 1,000 ms, unless it needs what the turn returned | 1,126 | 9 | 9 | 16 |
| within 2,000 ms | 932 | 1 | 1 | 202 |

| After the turn's last response, with nothing awaiting one | Calls | Soonest | Median | 90% within | Longest |
|---|---|---|---|---|---|
| the same LLM turn | 187 | — | 218 ms | 572 ms | 3,315 ms |
| a new LLM turn | 848 | 850 ms | 4,006 ms | — | — |

A turn's last response is the first response to its last call, which is the server's. When a flow's lookups ride in the result, the agent gets it later, so the gap after a served call counts the lookups' time too. That makes a split likelier, never a merge.

Scripted agents pace their calls. A script that sends its next call within 500 ms of a result it does not use looks just like a turn's streamed calls. So the quickstart, the walkthrough and the console's test fixtures wait 0.6 s between calls.

## Promotion, as the proxy serves

`stretto promote` replays each recorded session against the flow and scores each lookup it would make. It now replays the session as the proxy serves it:

- **As each result comes back.** The flow decides after each call's result. It works from the calls that had returned by then. The calls of that turn still on their way are the agent's own, so the flow does not look them up. Before, `promote` split every turn into one call per turn. So the flow proposed the calls the agent had already asked for, and then counted the agent's own calls as the lookups being used.
- **Along chains.** After a lookup that the agent also made in a later turn, the flow decides again with the lookup's result in hand, as the proxy does. This goes on up to `--per-call` lookups, 8 by default, the proxy's `--flow-per-call`.
- **Used means used later.** A lookup is used when the agent makes the same call in a later LLM turn.
- **Only through promoted sites.** A promoted flow hands back at every other site, so it never chains through them. `promote` scores with chains through every site, promotes, and scores again with chains through the promoted sites only. It repeats this until the promoted sites stop changing.

### AgentDojo Slack, re-promoted

The published Slack flow ([benchmarks-2026-09-27-flows.tar.gz](benchmarks-2026-09-27-flows.tar.gz)), promoted on each agent's 12 training sessions exactly as live (`--decider reach --threshold 0.3`, the default bar). Each cell is the lookups used out of those the flow would make:

| Site, after | GLM-5.3, before | Now | Haiku 4.5, before | Now |
|---|---|---|---|---|
| `get_channels` | 4 of 7 | 4 of 7 | 4 of 6 | 3 of 6 |
| `read_channel_messages` | 13 of 13, **promoted** | 0 of 3 | 9 of 10, **promoted** | 0 of 10 |
| `get_users_in_channel` | 9 of 11, **promoted** | 0 of 2 | 6 of 6, from 2 tasks | 0 of 6 |
| `get_webpage` | 2 of 4 | 2 of 4 | 1 of 3 | 1 of 3 |

After a channel's messages or members, the agents read the next channels in the same LLM turn. The old scoring counted those reads as the flow's lookups being used. Some had reached the proxy when the flow decided, and the flow now leaves them to the agent: GLM-5.3's lookups after a channel's messages fell from 13 to 3. The rest came after the decision, in the same LLM turn. They no longer count as used, since the agent asked for them before it could see the flow's results.

Promotion now keeps no Slack site for either agent, so the promoted flow makes no lookups and runs as the baseline does. The live promoted arm, whose 8 lookups were all repeats, is not re-run.

### τ²-bench, the promotion study again

[The promotion study](promotion-2026-09-25.md) promotes GLM-5's retail and airline flows on each half of the test tasks and replays them on the other half. That is two domains, two deciders, three bars and two halves: 24 promotions. `promote` before and after this change kept the same sites in 23 of them. Each site's counts changed, since `promote` now also decides after the flow's own lookups. A flow serves only its promoted sites, so those 23 replay exactly as before.

The one that changed is D0's retail flow at bar a (`--min-used 0.5 --min-lower 0.3 --min-tasks 3`), promoted on the first half's tasks. Before, `get_product_details` passed with 11 of 17 lookups used (65%, lower bound 0.45). Scored as the proxy serves, 5 of 11 are used (45%, lower bound 0.24), from 2 tasks, and it is held back. Replayed:

| Retail, D0, both halves | Turns saved | Lookups | The agent's own | Detours | Episodes with a detour |
|---|---|---|---|---|---|
| not promoted | 294 (21.2%) | 630 | 590 | 40 | 23 |
| bar a, promoted before this change | 277 (20.0%) | 601 | 573 | 28 | 19 |
| **bar a, promoted now** | **277 (20.0%)** | **580** | **554** | **26** | **17** |

The flows and the replay have changed since that round, so these rows are on today's code. There, the unpromoted row has 656 lookups and 58 detours.

## What changes

- **The turn rule.** `stretto_trace::mcp::episode` applies the rule above (`SAME_TURN_MS`). It changes the turns that `learn`, `promote`, `audit` and the console read from a proxy's log. `mcp::episode_sent` also returns, for each call, how many results of its turn had come back when it was sent.
- **The proxy.** `stretto-proxy` decides at the site of the call whose result came back (`Episode::after_call`), and leaves the calls of its turn still on their way to the agent. Before, it decided at its turn's last call. It also looked up calls the agent had already sent.
- **`promote`.** It scores as above, and takes `--per-call`.
- **Scripted agents.** `examples/quickstart/run.sh`, `scripts/walkthrough.py` and the console's fixtures wait 0.6 s between calls.

## Reproduce

The rule's table, from [the live round's episodes](live-benchmarks-2026-09-27.md#the-episodes) ([rows](turns-2026-09-28.json)):

```bash
tar -xzf docs/results/live-benchmarks-2026-09-27-episodes.tar.gz -C /tmp
python3 scripts/turn_inference.py /tmp/live-benchmarks-2026-09-27-episodes --json turns.json
```

Slack's promotion, for one agent (Haiku with `claude-haiku-4.5`):

```bash
E=/tmp/live-benchmarks-2026-09-27-episodes
mkdir -p /tmp/flows sessions/glm-5.3
tar -xzf docs/results/benchmarks-2026-09-27-flows.tar.gz -C /tmp/flows agentdojo-slack.flow.json
for d in $E/agentdojo-train/glm-5.3/baseline/slack-*; do cp "$d"/log/*.jsonl "sessions/glm-5.3/$(basename "$d").jsonl"; done
stretto promote --flow /tmp/flows/agentdojo-slack.flow.json --sessions sessions/glm-5.3 --decider reach \
    --threshold 0.3 --out slack-promoted.flow.json --report slack-promoted.md
```

The τ²-bench rows, as [the promotion study](promotion-2026-09-25.md#reproduce) sets up, with `stretto` built at the commit before this change and at this one:

```bash
python3 scripts/promotion_study.py --tau2 ../tau2-bench --oracle-cache .oracle-cache \
  --python ~/.venvs/tau2/bin/python --domains retail --deciders arbiter --bars a --out runs/turns
```
