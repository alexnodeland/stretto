# The probability that matters, and a procedure stretto runs

Until this round, a read-only flow made a lookup when the habit's chance that the agent calls that tool *next*, times the chance its arguments are the agent's, cleared 0.3. Both numbers were stand-ins. A lookup pays off whenever the agent makes the call before its next write, since a read's result stays current until then. After a customer lookup, for example, the agent reads the user, then an order, then answers the customer, then reads a product. The threshold had been set by hand.

This round derives both, measures the change on nine agents in replay and on GLM-5.3 live, and moves the compiled telecom procedure into stretto. [The working paper](../../paper/stretto.md) states the model and the propositions; this page holds the runs.

- **The replay counted too much.** A recorded call was skipped when *anyone* had made it already, so an agent's repeats of its own calls counted as saved. The fix counts only what a flow lookup answered: 0.2–0.9% of turns per domain, and 3.3% for one agent.
- **The next-step chance understates the chance of use.** Lookups the habit scored 0.4–0.6 were used 94–97% of the time (GLM-5, retail). The same contexts, counted for the right event (`reach`), have an expected calibration error of 0.01–0.08 in every domain, against 0.06–0.16.
- **The threshold is a ratio of costs, and the costs can be counted.** Live, a detour cost 2,530 input tokens over the rest of its episode and a saved turn saved 6,000, so θ* = 0.30. Counted in the recorded episodes, retail's costs give the same θ*, 0.298. Airline's and telecom's give 0.12–0.13: their contexts are longer and their results shorter. Swept, the reach decider's utility peaks at θ* for four of six agent and domain pairs.
- **Nine agents the flow never saw.** At 0.3, the reach decider takes 86.4% of retail's read-only ceiling, against 76.2% for the next-step decider (+10.2 points, 6.7–14.2). Priced at each domain's own costs, it saves more input tokens per episode than the next-step decider in every domain: 1.6 thousand in retail, 0.6 in telecom, 1.7 in solo telecom, and 0.1 in airline, where the two make nearly the same lookups.
- **Live, with no model of its own.** GLM-5.3 took 27.9% fewer LLM turns (19.1–35.9%) on 28 retail and airline tasks against the paired run's recorded baseline. 21 passed, against the baseline's 24. The four tasks lost follow lookups that returned what the baseline agent's own reads had returned.
- **The compiled procedure is a stretto artifact.** `stretto-procedure` runs the telecom workflow from a file and matches the Python reference on all 40 held-out tasks. With GLM-5.3 on its hand-backs, the cascade passes 39 of 40 at 0.48 LLM turns per ticket.

## The replay counts only what a lookup answered

`pilot/check_flow.py` replays an agent's recorded episode with the flow serving lookups after each call, and skips a recorded call the agent would not have needed to make. It used to skip any recorded call that had already been made, by the flow or by the agent. So a turn in which an agent repeated one of its own calls counted as saved, though no lookup had answered it. That was 0.2% of retail turns, 0.8% of airline turns and 0.9% of telecom turns, and 3.3% for one agent.

A recorded call is now skipped only when a flow lookup answers it. The lookup must be the same call, not already used by an earlier recorded call, and must have returned what the recorded call returned. With no write since the lookup, the agent's or the customer's, it always did, because reads leave the state unchanged. After a write, only an equal result shows that the lookup still holds.

`--legacy` replays with the old rule and reproduces the published numbers exactly: GLM-5 saved 307 retail turns with 33 detours, and 67 telecom turns with 50. Every number on this page uses the new rule.

## The next-step chance understates the chance of use

With `--explore 0`, a replay logs every lookup the flow weighed at every decision, with its score and whether the agent made that call before its next write (`used`). `scripts/calibration.py` bins them.

For the habit's next-step score, the share used ran far above the score. GLM-5's retail episodes, with the four 2025 agents' flow:

| Score (p·ρ) | 0.05–0.1 | 0.4–0.5 | 0.5–0.6 |
|---|---|---|---|
| Used before the next write | 0.48 | 0.94 | 0.97 |

The habit's score is the chance of the tool's being called *next*. After a customer lookup, reading the user comes next and reading an order comes after it, and both get used.

## Counting the right event

`stretto learn` and `stretto compile` now also count, over the habit's histories, how often each action came before the agent's next write. That is `reach` in the flow IR ([formats](../formats.md#reach)). Each action is its own Beta–Bernoulli, backed off level by level exactly as the habit is:

```text
r_j(a | h_j) = (m(h_j, a) + α · r_{j-1}(a | h_{j-1})) / (n(h_j) + α)
```

Here `m(h_j, a)` counts the training steps after the history `h_j` from which the agent called `a` before its next write. The same counts, a different event. The `r_j(· | h_j)` need not sum to one.

`--decider reach` serves it with a rule for sets. Of the lookups whose arguments bind, it takes the one with the highest chance times its binding's, if that clears the threshold. The next decision weighs the rest again.

| Airline | 17,124 / 17,174 | 0.106 → 0.068 [−0.042, −0.029] | 0.104 → 0.092 [−0.015, −0.009] | 0.821 → 0.845 [+0.002, +0.047] |

## The threshold is a ratio of costs

Reads commute with each other and with the state until the next write, so the expected value of a set of lookups is a sum over lookups. The best set is every lookup whose chance of use before the next write clears δ/(β+δ): a detour's cost over a saved turn's value plus that cost (the paper's Proposition 3).

**Measured live.** The paired run measured both in input tokens. The flow's 17 detours carried 43,000 input tokens over the rest of their episodes, 2,530 each. Its 260 saved turns saved 1.56M, 6,000 each. So θ* = 2,530 / 8,530 ≈ 0.30, the threshold the pilots had set by hand.

**Counted offline.** Both costs can also be counted in recorded episodes, which report each LLM turn's input tokens, in the agent's own tokens:

- **β** is the input tokens of a turn in the read-only ceiling, plus its calls' tokens times the turns after it.
- **δ** is a detour's result tokens times the LLM turns left after the result that prompted it. It is averaged over the detours the reach decider made in the replays below.

Characters become tokens at each agent's own rate, fitted on how much its input grew between turns: 2.6–3.9 characters per token, and 6–10 for the Gemini models. Qwen3-Max's published episodes report no tokens, which leaves eight agents:

|---|---|---|---|---|
| Retail | 5,824 | 2,467 | **0.298** | 0.18–0.34 |
| Airline | 7,051 | 1,022 | 0.127 | 0.00–0.20 |
| Telecom | 8,929 | 1,178 | 0.117 | 0.02–0.22 |
| Telecom, solo (2 agents) | 8,885 | 541 | 0.057 | 0.02–0.08 |

The reach decider's utility peaks where θ* puts it in four of the six pairs: at 0.3 in retail for both agents, and for Sonnet 4.5 at 0.15 in airline and 0.1 in telecom. The other two peak at 0.4–0.5, for reasons the page can name:

- **GPT-5.2 without reasoning, telecom.** It used 2% of the lookups scored 0.1–0.3 (mean score 0.21), where the five other pairs swept used 14–25% of theirs (mean scores 0.15–0.24). θ* is a threshold on the true chance, and scores counted on other agents overstate this one's.
- **GLM-5, airline.** Its lookups scored 0.1–0.3 were used about as often as scored (14% at a mean of 0.15), but going from 0.3 to 0.1 added 23 uses and only 4 saved turns. A turn is saved only when all its calls are answered, and airline's turns hold the most parallel reads (22% of the ceiling's turns).

At its best threshold the reach decider beats the next-step decider's best by 10–14% in retail and in Sonnet's airline, and by 2% in Sonnet's telecom and GLM-5's airline. It trails it by 9% for GPT-5.2 in telecom. It is also robust to the threshold: past its peak its utility falls slowly, where the next-step decider's collapses beyond 0.4–0.5, since next-step scores seldom exceed one half.

## Live

Live, `stretto-proxy` serves the flow between GLM-5.3 in Claude Code and τ²-bench's tools over MCP, and the customer is GLM-5.3 as τ²-bench's user simulator. The reach arm serves the flow learned from the four 2025 runs at 0.3. It asks no model: `--flow-oracle mock` is never consulted, because the reach decider needs no answer. It ran on 20 retail and 8 airline test tasks, drawn at random (seed 26) from the paired run's 40 and 20. Each is compared with [the paired run's](paired-2026-09-25.md) recorded baseline on the same task; in airline that is the mean of its two trials. D0, the earlier flow, was recorded in the same run.

| | Tasks | LLM turns, baseline → reach | Change | Input tokens | Passed: baseline, D0, reach |
|---|---|---|---|---|---|
| Retail | 20 | 227 → 154 | **−32.2%** [−40.0, −23.5] | −25.4% [−34.7, −16.0] | 17, 14, 16 |
| Airline | 8 | 83.5 → 70 | −16.2% [−37.2, +10.6] | −12.9% [−42.1, +31.0] | 7 (7.5), 7, 5 |
| Both | 28 | 310.5 → 224 | **−27.9%** [−35.9, −19.1] | −21.9% [−32.9, −9.9] | 24, 21, 21 |

D0 cut the same tasks' turns by 26.4% in retail and 13.8% in airline. The reach arm took fewer turns than the baseline on 23 of 28 tasks and the same number on one.

**The replay's assumption, live.** A replay counts a recorded call as answered when a lookup returned the same result earlier, assuming the agent would not make the call itself. Live, the flow made 101 lookups in the 28 episodes, and GLM-5.3 made none of them again before the next write. It also never repeated one of its own 57 reads.

**Passes.** Against the baseline's first trial, five pairs disagree. Four passed only without the flow and one only with it (McNemar p = 0.38). In each of the four, every lookup the flow made returned what the baseline agent's own read had returned, and the episodes parted later:

- **Retail 38.** The customer gave another reason for cancelling ("ordered by mistake" against "no longer needed"), and the database check compares the reason.
- **Retail 71.** The customer changed two items where the baseline's customer changed their mind about one.
- **Airline 31.** Asked for an exception on a basic-economy booking, the agent upgraded the cabin and changed the flights. Both baseline trials refused. D0's agent did the same as the reach arm's, and failed the task too.
- **Airline 32.** The agent searched a route through Miami and priced an upgrade at $396, which the customer declined. The baseline searched Newark to Los Angeles, direct and one-stop, and made the change in two steps.

Two of the four are the simulated customer's choices. The other two are the agent's decisions after a customer's plea, with the same records in its context as the baseline's. Eight airline tasks cannot tell a flow's effect on later decisions from GLM-5.3's own variance, and we claim neither. The 80-pair paired run, whose D0 flow made the same kind of lookups, lost 1.25 points (−7.5 to +6.25).

## The procedure in stretto, and the cascade

[The compiled telecom workflow](telecom-workflow-2026-09-26.md) was a Python script. It is now data, the procedure IR (`stretto_procedure: 1`, [the published one](telecom-workflow-2026-09-26.procedure.json)), and `stretto-procedure` runs it against any MCP server over stdio. The file holds:

- a decision tree per site;
- the provenance of every identifier;
- the checks of the ticket's stated outcome;
- the guard against repeats;
- the transfer to a person.

The verdict is `resolved`, `transferred` or `hand_back`.

On all 40 held-out solo tasks, `pilot/run_procedure.py --compare` found that stretto's runtime made exactly the script's calls, with the same rewards and verdicts. It passed 35, transferred 11 to a person as the policy directs, and handed back 4, all four failures.

The cascade gives each hand-back to a model, which takes over from the procedure's state with the procedure's calls and results as its context (`run_episode.py --handback`). Live, GLM-5.3 in Claude Code on τ²-bench's solo protocol resolved all four hand-backs in both of two trials, at 4.75 LLM turns each. On the same four tickets from scratch, it resolved three, in 12–19 turns. On four other tickets it also resolved three, in 14–21. So the cascade passes 39 of the 40 held-out tasks and makes 0.48 LLM turns per ticket, where GLM-5.3 alone made 15.9.

## Caveats

- **Replay assumes the agent skips what it already has.** A replay counts a recorded call as answered when a lookup returned the same result earlier. It assumes that the agent, seeing that result, would not make the call, and otherwise acts as recorded. Live, GLM-5.3 re-made none of 101 lookups; other agents are untested.
- **Costs are measured once.** β and δ come from one live run of one model on retail and airline. Other models, prices and latencies move θ*, and so may telecom's longer episodes.
- **The live runs are small.** They bound turns, not success: a pass-rate interval of a point would need thousands of paired tasks. The baseline was recorded a day before the reach arm.
- **Solo's flow is its agents' own.** Only two solo runs are published, so the solo flow was learned from the same two agents' training episodes, not from other agents'.

## Reproduce

The flows every replay and live run on this page served are published: [retail](reach-2026-09-26-retail.flow.json), [airline](reach-2026-09-26-airline.flow.json), [telecom](reach-2026-09-26-telecom.flow.json) and [solo telecom](reach-2026-09-26-solo.flow.json). Each was learned from τ²-bench's four 2025 runs (`$R` is `tau2-bench/data/tau2/results/final`; solo telecom's from the two `no-user` runs):

```bash
stretto learn --results $R/claude-3-7-sonnet-20250219_retail_default_gpt-4.1-2025-04-14_4trials.json \
  --results $R/gpt-4.1-2025-04-14_retail_default_gpt-4.1-2025-04-14_4trials.json \
  --results $R/gpt-4.1-mini-2025-04-14_retail_base_gpt-4.1-2025-04-14_4trials.json \
  --results $R/o4-mini-2025-04-16_retail_default_gpt-4.1-2025-04-14_4trials.json \
  --tau2 tau2-bench --domain retail --habit-only --out pool-retail.flow.json
```

A replay, at one threshold, with every weighed lookup logged (`scripts/fetch-leaderboard.sh all` fetches the nine agents' results):

```bash
cd pilot && python check_flow.py --domain retail --trials 0 1 2 3 --results RESULTS.json \
  --flow pool-retail.flow.json --flow-oracle replay --oracle-cache CACHE --flow-decider reach \
  --flow-threshold 0.3 --explore 0 --in-process --jobs 4 --out OUT
python scripts/calibration.py OUT... --json calibration.json
python scripts/ceiling.py RESULTS.json... --json ceiling.json   # the read-only ceiling per episode
python scripts/costs.py RESULTS.json... --replays DIR --json costs.json   # β, δ and θ*, counted
```

Live (GLM-5.3 as agent and customer, one task; `--arm baseline` for the other arm):

```bash
cd pilot && python run_episode.py --domain retail --task-id 38 --arm reach \
  --flow pool-retail.flow.json --flow-oracle mock --flow-threshold 0.3
```

Whether the agent made a lookup again, from the published episodes:

```bash
tar xzf reach-2026-09-26-episodes.tar.gz
```
