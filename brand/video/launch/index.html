Read ahead of your agent.
In a fugue, a stretto is where the entries of the subject overlap.

An agent spends an LLM turn on every call.

Many of those turns are decided by what the tools returned.

stretto makes those reads for the agent.

Tool-using agents spend most of their cost in the LLM turns that decide the next call.

The first result named the orders, so turns 2 and 3 were fixed by the tools, not by the customer.

After each call, the reads the agent would make next ride in the same tool result, and it skips those turns. A wrong read costs tokens and changes no state.

stretto-proxy wraps any MCP server: the host runs it in place of the server's command, and it records each session.

How it works

2 · Learn

In the sessions
→ get_user_details {"user_id":"user_7"}
← {"orders":["#W7a","#W7b"],…}
→ get_order_details {"order_id":"#W7a"}
In the flow
after get_user_details
  look up get_order_details
    order_id ← get_user_details
               at $.orders[*]

stretto learn counts which reads follow which calls, and where their arguments come from. The flow is a JSON file you review like code.

How it works

3 · Serve

The tool result the agent receives
→ get_user_details {"user_id":"user_7"}
{"email":"c7@example.com","orders":["#W7a","#W7b"],…}
--- Also looked up automatically (current results; no need to repeat these calls) ---
get_order_details {"order_id":"#W7a"}: {"order_id":"#W7a","status":"pending",…}
get_order_details {"order_id":"#W7b"}: {"order_id":"#W7b","status":"pending",…}

After each of the agent's calls, the flow's lookups ride in the same result. No new tool, no change to the prompt.

How it works

When to make a lookup

Make it when P(used before the next write) ≥ δβ + δ
β what a saved LLM turn is worth: about 6,000 input tokens
δ what a detour, an unused lookup, costs: about 2,530
So the threshold is about 0.3. Live paired run, GLM-5.3, τ²-bench retail and airline.

The reach decider asks no model. It counts, in the sessions, how often each read was used before the agent's next write.
